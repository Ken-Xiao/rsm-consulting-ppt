# ADR-0008：V2 能力路由边界——读路由表与激活能力分两层

- **状态**：已采纳（含对 D9 登记前提的更正）
- **日期**：2026-10-03

## 背景

D9 登记时的前提是：D7 轮小任务测试中，执行者"夹带"了 `v2-capability-router`。**第六轮侦察推翻了这个前提。**

全库 6 处涉及该文件"何时加载"的表述里，**没有任何一处明写"小任务不读该文件"**；相反，`progressive-loading-protocol` 的 Layer 0 把它明列为 Always Loaded（"每个任务都应优先读取"），express 档位的下限列也含它。执行者是照着 Layer 0 的原文执行的——它没有夹带。

真正的缺陷是**同一件事两种口径**：

| 口径 A：每任务都读 | 口径 B：按需读 |
|---|---|
| `progressive-loading-protocol` Layer 0（明写） | `SKILL.md` L84 旧句"按需读取"（歧义） |
| `SKILL.md` express 行下限列（明写） | `task-tier-protocol` L5"涉及…时读取"（条件） |
| `v2-capability-router` L3"读取 task-tier-protocol 后使用" | `INDEX.md` L30"按需启用"（歧义） |

这解释了为什么两轮执行者会得出相反结论——**各自引用的都是真实存在的规则**。

**连带更正**：D7 轮的 judge 判据里把这一条写成了"小任务默认不加载"，等于把一处误读写进了地面真值。这是本项目**第三次评测工件失真**（前两次：D3 摘要漏写关键信息、D5 第二实例的工件缺陷）。写判据的人自己也会误读 skill——判据里的每一条"地面真值"都必须回链到原文核验。

## 决策

用户确认方向：**澄清措辞，保留"各档位都读"**（否决了"改为纯触发式"——那会与 Layer 0 和 express 下限列冲突，需动分层结构）。改动 2 处：

1. `SKILL.md` L84 改写为**显式两层**：
   > 读这张路由表不等于「加载 V2 能力」——它是判断本任务该激活哪些能力的入口，各档位都要读（Layer 0）。受档位限制的是**激活哪些能力**：`express` / `quick-polish` 只激活 Tier Defaults 列出的基本项，不得加载完整 V2 能力集，也不得因激活某项能力而抬高档位或交付等级。
2. `references/task-tier-protocol.md` L5 对齐（原是异类）：
   > 确定档位后读取 `references/v2-capability-router.md`，按其 Tier Defaults 只激活本档位默认能力，不加载完整 V2 能力集。

`SKILL.md` 51,862 → 52,207 字节。

## 为什么否决"纯触发式"（原登记方向）

把该文件从 Layer 0 与 express 下限列移出、统一由触发条件控制，会：① 直接与 Layer 0 的明文冲突，需要改分层结构；② 让 express 档位失去"本档位默认激活什么"的唯一指引（该指引就在 Tier Defaults 表里）；③ 触发条件"涉及 V2 增量能力"几乎对所有档位都成立，等于没有触发。**成本更高、收益更小、且制造新冲突。**

## 后果

### 需要接受

- 体积 +345 字节。
- **遗留观察**：小任务执行计划偶发漏掉一个必读件且无规则依据（两次 P1 样本各漏一个不同文件）。若复现，优先排查新句"只激活基本项"是否被从**能力**过度泛化到 **reference 加载集**——那将是 D5 形态的第四实例。

### 得到的

- 消除了"每任务都读 vs 按需读"的双口径；两处异类表述对齐。
- "读路由表"与"激活能力"两层显式分离，激活纪律（Tier Defaults、不得抬高档位）有了单一句子可引用。

### 验证结果

3 prompt × 2 spec，**12 个盲评 judge**（X/Y 位置随机交换）：

| Prompt | 任务 | 结果 |
|---|---|---|
| P1 | quick-polish 执行计划 | 第 1 次 2-1 支持改动前；复采样 2-1 支持改动后（合计 3-3） |
| P2 | client-ready 执行计划 | **3-0 支持改动后**（slight ×3） |
| P3 | 审阅含误读的加载计划草案 | **3-0 支持改动后**（2 slight + 1 clear） |

**总 9-6 → keep**。改动所针对的维度 **6-0 一致**：改动前执行者把路由表定性为"按需读取"（错误）且激活能力后不读其 Required reference；改动后执行者逐字引用澄清后的规则，并点名 `auto-fix-playbook.md` / `language-calibration-standard.md`。

### P1 反转的处理（复采样，不是修工件）

第 1 次 P1 跑出 2-1 支持改动前。按 D3 纪律追查：三个 judge 的决定因素都是 `failure-modes.md`——但 `diff` 确认两版 spec 仅 2 行差异且都不涉及该文件，且 D7 轮同版本执行者明确纳入过它。判定为**正交的执行者方差**。方差的标准处理是复采样：第 2 次 P1 翻为 2-1 支持改动后，且漏的文件换成了 `strategy-brief.md`——两次漏的是不同文件，进一步排除系统性规则效应。**经验：反转追查的结论若指向方差而非工件缺陷，处理方式是复采样，不要回头改方案。**
